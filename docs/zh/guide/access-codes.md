# 访问码

**访问码**让控制端只需在连接框输入一串短码即可连上一台在线被控端，无需知道对方地址。它有两种，且**同一个输入框都收**，由服务端自动识别输入的是哪一种：

- **设备码**：每台在线被控端都会显示的**长期**码，随时用它重新连接该被控端。
- **支援码**：带**有效期（TTL）**的设备码，为一次性协助按需签发。签发支援码需要**中心大脑**（manager）；纯信令服务器只路由连接，**不签发**支援码。

## 兑换码

在连接框输入码并提交（`POST /api/desk/redeem-code`）。服务端把它解析到目标被控端的 live 连接，返回一个**能力受限会话**。在开源信令服务器上，兑换出的会话**恒为能力受限**——完整、不受限的控制只属于**用账号凭据直接登录**（会话 Cookie）的单账号 owner，而非任何兑换码。

每次兑换都带一个**访问能力上限**——即 owner 为该码配置的能力上限（见下）。该上限会随会话期间控制端发出的每个控制请求一同携带。

## per-code 能力上限

owner 可**为每个设备码**配置一个**能力上限**，约束被兑换的（非 owner）会话能做什么。每项能力为三态：

- **允许**：放行（仍受被控端自身全局访问设置约束）。
- **询问**：动作发起的那一刻弹框询问被控端本地用户。
- **拒绝**：硬拒。

预设可快速套用——**仅查看**（全部拒绝：投屏 + 只读诊断）、**协助**（折中）、**完全**（全部允许）——也可逐项设定：远程控制、剪贴板、私有屏、白板、终端、文件浏览、文件传输。

**未配置**上限的码默认取**全询问**的受限姿态（每项能力都弹框），绝不默认全权。

## 最终生效权限如何裁定

码的上限只是**上界**。每个动作实际生效的能力，是**三者取更严（meet）**：

1. **码的能力上限**——owner 为该码允许的；
2. 被控端的**全局访问设置**——`config.toml` 的 `[security]`；以及
3. 被控端的**现场审批**——当 (1) 与 (2) 取 meet 后仍为「询问」时，弹框询问被控端本地用户。对于访问码 / 支援会话，该次选择**只对当前这一个请求生效**，绝不会写入被控端的全局访问设置——借来的会话在现场弹框里的「记住」永远无法放宽 owner 已配置的能力（owner 自己的会话仍保留常规的「记住」行为）。

因此任一处为**拒绝**即硬拒；任一侧某维未配置一律弹框；只有**上限与全局都为允许**才是唯一免弹框放行的组合。强制**完全在被控端侧**——兑换时返回的上限只是给控制端的 UX 提示，绝非安全边界。
