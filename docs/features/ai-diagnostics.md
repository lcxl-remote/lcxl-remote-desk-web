# AI Diagnostics

Desktop context can be selected manually with **Add context**, or requested by the assistant for the current question: desktop session inspection, semantic UI inspection, or current-screen capture. A new conversation with no attached context can request these reads. Approving the permission card automatically continues the original question; rejecting it performs no read. Authorization is bound to the device and current input, with expiry and usage limits; a new request is required when it expires or is exhausted. Screenshots require an image-capable model. Read approval does not authorize mouse or keyboard input, and cannot bypass an offline device, missing OS permissions, or locally disabled capabilities.

In an existing conversation, select **Schedule this conversation** to open Scheduled tasks, then enter the instruction and one-time execution time and confirm. The server atomically creates and enables the timer; no draft or second activation step is needed. The device and conversation stay bound to the original conversation. Times are entered in the selected display time zone and stored as UTC. If the original requirement revision has changed, creation or activation is rejected; return to the conversation to schedule it again. Use the Conversation continuations tab to manage tasks and view results through run history. Completed tasks retain rename, delete and history actions, but cannot be rescheduled. To continue again, create a new scheduled task from the original conversation.

An enabled conversation timer survives ordinary follow-up chat, including “confirmed”; only an explicit pause or cancellation stops scheduling. When due, it waits for the conversation to become idle and executes the approved task text in the latest conversation context. Dispatch pins the current input revision, so new input during execution still fences the older turn. Permissions are rechecked without extending expiry or scope.

Select **Task contract** on an automation to view its saved revision, run limits, sending account and recipients, and automatic resource and operation scopes. If no contract is saved, select **Generate review contract from guided run**. The server derives scopes from verified reads and action receipts in the latest completed guided run, binds the account identifier and recipients from the receipts, and checks message data sources. Generation saves an unapproved contract without granting permissions or enabling the task. Incomplete evidence or distinct operations of the same tool that cannot be consolidated prevent generation. Attachments require verified file creation receipts from that same run. This action does not overwrite an existing contract. Draft preparation and sending retain separate permissions: a verified draft can support variable text, but cannot prove sending. Gmail extension page references and draft snapshots now bind the visible signed-in account, which is used for send validation and contract destinations. An unavailable account prevents extension draft preparation and sending. Slack requires a verifiable workspace and member identity from the extension page; a browser profile alone is insufficient. Missing or ambiguous identity blocks draft preparation and sending. Actual Slack page compatibility still requires acceptance testing. Sending across independent runs still requires complete acceptance testing. Viewing alone does not approve permissions. When the saved contract matches the current task version, select **Check guided run for publication**. After a matching completed guided run is found, explicitly accept the permissions, fixed destinations and budgets, then select **Approve and publish**. The server rechecks current permissions and verified guided-run evidence before enabling scheduling. Authorization has no automatic expiry by default; use Revoke task authorization to revoke it. Publication does not mean execution succeeded; the complete independent-task execution and real-send flow is still under development and validation.

On the controlled device, sign in as owner and open **Local AI Policy → Local web message permissions**. Read the current policy, explicitly choose the Computer Use master, browser extension, draft preparation and message sending switches, then save. Enabling sending does not enable the other switches or approve a message or automation. Saving requires the device worker to acknowledge the same policy revision; capability listings then refresh with the device heartbeat. A conflict or uncertain application requires a new read, without automatic retries. Manager and remote pages cannot change these local switches. Disabling them blocks later undispatched operations; it does not recall messages already sent.

The Gmail extension send adapter compares the visible Google account at page snapshot time with the account immediately before activation. A missing, ambiguous or changed account returns DefinitelyNotSent without clicking. An account change after activation leaves OutcomeUnknown; a notice from another account cannot prove delivery. The account identifier also travels with the page reference into the draft snapshot and review contract. A new independent run must verify the same account; the complete background execution and real-send flow still require acceptance testing.

Tool results, user messages and AI replies are conversation history and are not removed from model context merely because time passes or an execution authorization expires. Window trimming or summary compaction occurs only when the context capacity threshold is reached; the original transcript remains stored. Historical results describe what happened at the time, not the current device state, and do not authorize another execution. New actions still validate authorization deadlines, target identity and required current state. Changes to model destination or source authorization can still restrict disclosure of affected content.

## AI Assistant conversations

Internal server messages used to resume a conversation are omitted from restored chats, conversation titles and message counts. They remain in the stored execution context and are not treated as new user input or additional permission.

Native macOS text-file operations do not require semantic observation or a foreground application. The Computer Use master switch, conversation directory scope and per-operation authorization still apply.

Web, iOS and Android update/delete confirmation cards show the file name, full SHA-256 and source call ID from the device receipt. Updates also show the exact matching and replacement text, or the complete replacement; deletion is explicitly recoverable. Each approval permits one exact operation. Missing verifiable review details block approval; the AI's stated reason does not replace those details.

File operations retain the device Computer Use master switch, with no separate file-creation toggle or device-wide directory allowlist. Open Directories in the current AI Assistant conversation and add a directory on the controlled device, or approve a directory proposed by the AI. Directories must exist and use canonical absolute paths; a changed resolved path needs another review and confirmation. Consent belongs only to this conversation, survives refresh, can be revoked, and is not inherited by a new conversation. Directory references last 24 hours and their identity is checked on use; remove and add the directory again after expiry. Directory consent does not approve all file operations: read egress, creation, updates and deletion each retain their operation-level authorization. After approving a directory request, send “Continue” so the AI can request the specific operation. Creation never overwrites an existing file, supports empty UTF-8 text, and has a 64 KiB write limit.

The macOS text tools include `update_text_file` and `delete_text_file`; capability listings retain the original keys alongside localized descriptions. Updates replace all text or one unique matching fragment. They bind the complete file version and SHA-256 from a verified read, creation or update receipt in the current conversation. Every update/delete requires exact confirmation and a one-use grant. Directory metadata lists immediate children only; reading a child's contents and sending them to a model need separate authorization. Truncated reads cannot justify a full overwrite. Links, out-of-scope targets and version conflicts are rejected.

Updates and deletions retain a private recovery directory beside the target: `approved-before.txt` is an independent approved-before copy; deletion also moves the original file to `original` there. There is no permanent-delete fallback. Web file receipts are collapsed by default and show name, bytes, digest and recovery location when expanded; unrecognized formats remain raw. A post-commit concurrency conflict is reported as unknown, with recovery evidence retained and no automatic rollback or retry. Inspect the target and recovery copies before acting; do not overwrite a concurrently created file. Unknown-result recovery receipts remain available when reopening the conversation.

In the Web UI, “Command result (from device)” is collapsed by default; select its title to expand it. Standard receipts show the exit code, execution time, and stdout/stderr; terminal mode retains combined output. Empty output, truncation, and redactions are labeled. The original receipt can be expanded separately. Non-JSON or unrecognized formats are shown unchanged, without altering the saved result or AI interpretation.

Older conversation history does not expire with time. Model destination and source authorization are still checked before disclosure. New terminal errors are saved with the conversation, so refreshing or reopening displays the same specific reason; a new turn clears the previous error. Errors not saved before upgrading cannot be reconstructed.

System settings → Context management (`/system/context-management`) switches between checkpoint summaries and window trimming. Summaries are on by default. Changes apply on the next turn and survive restarts. Compaction makes an additional call to the current model and may incur charges; failures are explicit, without silent fallback to trimming.

Isolated background command interpretation does not reset the regular conversation's context meter baseline; new results and replies still count. Actual summary compaction and history-window trimming produce distinct short system notices in the conversation area, also restored with the session. These notices do not mean the original chat was deleted. A baseline overwritten by an older version's isolated interpretation refreshes on the next regular model preparation.

AI natural-language replies use the interface language supplied when sending a message. Permission resumes and background follow-ups inherit the saved conversation language. This preference does not change tools, commands, JSON fields, or permissions. Existing conversations without a saved preference record it on the next normal message.

On continuation, AI retrieves history on demand. Elapsed time does not make historical content unavailable; disclosure must still be authorized for the current model. Historical commands are not automatically replayed.

The ring at the left of the Send row shows context budget occupancy. Hover or focus it to see the compaction/trimming threshold, used bytes, remaining budget, and estimated text draft increase. The threshold is the latest prepared history budget after reserving system prompt and tool overhead. Summaries, retained messages, and subsequent replies and tool results count toward usage. Tool or context changes can alter the next budget, and the draft estimate excludes attachments not yet read; remaining bytes are not an exact character allowance. Usage is recalculated from the retained window after compaction/trimming. Missing usage displays “—”, not zero; an existing conversation needs a new model request preparation to produce this metadata.

Only pending requests or requests needing revalidation appear in the main area. Resolved requests are hidden by default; use the Permission request history icon to review their status and details in a scrollable panel. Approval does not imply successful execution.

On the bottom row of the composer, alongside Send, the left side contains the context ring, Task details icon, then Permission request history icon. Hover to see their names and select an icon to open its panel. The top-right Task details text button is no longer shown.

Compaction/trimming notices stay at their recorded message boundary and display the server-recorded time; later messages do not move them. Unlocated older records appear in collapsed history, with missing times marked as unrecorded rather than replaced by refresh time.

Background command interpretation has no tools. Invocation markup emitted as prose is withheld and corrected at most once; a repeated failure produces an explicit error. The original command result remains available, and commands in prose are never executed.

The conversation header contains **Conversation history** and **New conversation**. There is no separate connection status row. The icon before the conversation title is green when signaling is connected, amber while connecting, and gray when the assistant is disabled. Hover for its status explanation; screen readers can also read it. Hover over the conversation title to see the selected target name. History lists the 100 most recent conversations for the current device; select one to restore and continue it. You can browse the list during a task or request, but switch only after it finishes. Empty conversations use only the input placeholder, without a duplicate explanatory paragraph.

In addition to manual control, LCXL Remote Desk lets AI models **read and analyze** device state and, when the authenticated owner explicitly approves a command, act on the diagnosis.

## How It Works

AI is orchestrated by the **central signaling server** (the "central brain"). The device is a **thin edge** that supplies read-only evidence on request; owner-confirmed commands return through a separate, sealed execution path. When a user asks a question during a session (e.g. *"Why is this system slow?"*), the central server drives a strict pipeline:

![AI diagnostics and owner-confirmed execution flow](/architecture/ai-diagnostics.svg)

1. The central brain requests **read-only evidence** from the edge (system info, processes, ports, logs, screenshots).
2. The edge **collects and redacts** the evidence locally — redaction **fails closed**, and raw screenshot bytes are stripped before anything leaves the host.
3. The central brain **calls the model** (only after the edge's redaction succeeds).
4. The central brain runs a multi-turn tool loop and streams the answer back to the browser.
5. If the model requests `exec_command`, the loop parks. The browser shows the complete shell, command, working directory, timeout, and server-authoritative risk; only an explicit approval resumes dispatch.

The diagnosis panel has explicit resize handles: drag its left edge to change
the width, its bottom edge to change the height, or its lower-left corner to
change both. Drag the title bar to move the panel anywhere within the remote
desktop view. While the view is at the bottom, streaming output follows the
latest text automatically. Scrolling up pauses that behavior and shows a
down-arrow button that returns to the latest content without losing the
reader's place unexpectedly.

## AI Assistant Exact Command Grants

AI Assistant uses its itemized permission card for owner command approval, without a second legacy diagnostic dialog. In confirmation mode, an owner may request non-blocklisted commands outside the template catalog, including `du`, `df -h`, pipelines and multiline scripts. Read-only/suggestion-only modes, non-owners and shared access do not gain execution authority.

Review the complete original command, shell, working directory, target device/session, effective timeout and stdout/stderr limits. An omitted working directory uses the execution process default, not necessarily the home directory. Off-template commands are Critical and potentially mutating: the blocklist is not a shell sandbox, the shell interprets the approved script, and elevation is not automatic. A grant permits one execution of the frozen plan. Changed input, plan, target session or policy requires fresh approval. Unknown outcomes keep the original task and are never automatically resent. Missing or invalid command review data cannot be approved.

Ordinary noninteractive commands do not require a PTY or foreground application. Offline targets, system permission errors, timeouts and cancellation are reported as observed.

When a background command finishes, Web AI Assistant separately displays the original result saved by the device, including timeout failures; this is not an AI-generated answer. Newly approved exact commands freeze their result-interpretation deadline at dispatch: the approved maximum runtime plus five minutes for delivery and interpretation, capped by the session scope's expiry. Running longer than five minutes within that window does not require a second approval to interpret the result. This changes neither the approval-wait deadline nor the command's execution timeout.

Automatic interpretation sends only the corresponding user requirement and this result to the original model, not old screenshots or the entire history, and cannot launch another command. Revocation, model/context changes, a superseding requirement, an invalid result, or actual interpretation expiry still stops the follow-up while retaining the original result. Upgrades neither retroactively authorize completed old tasks nor rerun commands.

On the controlled device, **System settings → AI policy → Maximum runtime per command** accepts 10–7200 seconds and defaults to 600 seconds. Execution is also bounded by the duration requested on that command's confirmation card. Moving to the background does not reset the clock, and increasing the device ceiling does not extend an already approved command.

## Key Properties

- **Thin Edge** — the device never runs model inference or holds provider credentials; it only collects and redacts evidence when the central brain asks.
- **Read-Only Data Collection** — system info, processes, ports, logs, and optional screenshots, gated locally by the edge collection policy. A screenshot is offered only to a model declared image-capable; the original image is kept only while the active turn needs it, then replaced by bounded text metadata instead of being retained in conversation history.
- **Model Agnostic** — compatible with both OpenAI-compatible and Anthropic endpoints, configured centrally.
- **Suggest-Only Defaults** — the model proposes fixes; execution requires explicit user confirmation, capped by each device's local execution ceiling.
- **Owner-Confirmed Actions** — in Confirm Each Action / Session Approved mode, the authenticated owner may approve an off-template PowerShell, pwsh, bash, or sh command. It is always shown as **Critical** and only the effective blocklist is claimed to have been checked.
- **Target-Verified Shells** — the Desk Server runs a bounded, side-effect-free probe for the executor-supported interpreters when it connects. The model's `exec_command.shell` schema lists only the verified intersection and marks the first entry as preferred. If a model still requests another shell, it receives `unsupported_exec_shell` with the current available list and may retry without opening an approval.
- **No Autonomous Approval** — the model may request a command, but it cannot approve its own request. Fleet, automation, MCP, shared-access, and non-owner paths remain template-only or non-executable.
- **Bounded, Continuable Turns** — the central loop stops after too many calls to the same tool type. Completed output and tool results remain visible and persisted, so the user can send a follow-up such as “continue” in the same conversation.
- **Durable Background Commands** — an approved command that is still running after **8 seconds** becomes a background task instead of blocking the diagnosis turn. The dispatch receipt returns the task ID to the model as a structured field, while the diagnosis panel shows a localized “Moved to background” state with the same ID so the user, model, and later completion event can correlate it precisely. The command keeps running until it completes, the operator cancels it from the diagnosis panel, or it reaches the device-local **command runtime limit**. That limit is configured under the Desk Server's Local AI Policy, defaults to **600 seconds**, and accepts **10–7200 seconds**; it is independent of the 8-second foreground threshold. Saving a new limit automatically refreshes the host's central signaling registrations, while the host immediately enforces the saved value as its authoritative ceiling. Portable/open-source Signal stores the task and its completion in SQLite, exposes it through `wait_for_task`, replays pending completion delivery after a Signal restart, and asks the host's execution ledger when a live result was missed. Once the durable result arrives, Signal fires one bounded, read-only follow-up turn so the model interprets the result without waiting for another user message; that turn cannot execute a new command. The Manager path provides the same completion-follow-up behavior through its distributed work ledger when the administrator enables automation.
- **Readable Answers** — assistant prose is rendered as GitHub-flavored Markdown, including headings, lists, code, and tables. Raw HTML is ignored and model-supplied image URLs are not loaded.
- **Recoverable Conversation View** — both Manager and Portable/open-source Signal expose the same persisted conversation snapshot. If a terminal live event is missed, the panel recovers the settled answer and tool results instead of remaining stuck on “Awaiting approval”.
- **Inspectable Tool Calls** — select any item in the tool timeline to expand the model-produced JSON input and the redacted, bounded output returned to the model. The details remain available in settled turns and restored conversation history.
- **Shared Core** — the transport-neutral diagnostic logic lives in the `desk-diagnose-core` crate, reused by the central brain so behavior never drifts.

Owner-selected file, directory and terminal attachments store only bounded display metadata, opaque device references and source labels, not their contents. Selection does not grant execution authority. Open-source Signal atomically saves each new metadata operation and its first receipt in SQLite. Retrying the same request returns that original `changed` value, including after reconnecting or removing model configuration; it does not modify the attachment, switch its model destination, extend expiry or reactivate a detached selection. Reusing the request ID with different operation data is rejected. Detaching an existing attachment needs no configured model. New mutations are refused while a turn is active; a historical receipt can still be replayed after the current owner and target checks. A receipt is not proof of the attachment's current state: refresh the authoritative conversation snapshot. The original device still validates each reference when data is read; metadata receipts alone do not establish complete object-read or mobile-control acceptance.

If retained selection metadata has no original receipt, Signal cannot reconstruct the first result from it and rejects that request ID. Refresh the snapshot and submit a new explicit operation with a new request ID; existing attachments and permissions are not rewritten during upgrade.

Live capability selection uses `UpdateDeviceAssistantContext` (638) → `DeviceAssistantContextUpdated` (639) on both Signal and Manager. A selection saves bounded metadata tied to the current worker incarnation, model destination and readiness expiry; it grants no tools and contains no screen or document content. `CurrentScreen` remains an explicit one-turn input and cannot be saved by 638. The same complete request returns its first `changed` result, including false, without refreshing metadata; another selection under the same request ID is rejected. Clearing live selection needs no configured model and does not remove file or terminal attachments. New selection updates refuse active turns even after their lease expires; normal recovery must settle those turns first. Success and failure preserve transport and client request correlation. Always refresh the session snapshot for current state rather than treating a historical receipt as an active selection. This metadata exchange alone does not establish complete live-read or mobile acceptance.

For new AI Assistant inputs, Signal saves the exact read-tool and object selection atomically with the message. Reusing a message ID with different text, source labels, subject or selection is rejected. Permission continuations restore that original selection and deadline; later attachments or newly ready read tools do not expand it. Legacy inputs without an original object selection do not acquire one automatically. Before sending an object read and after receiving its result, Signal rechecks the current input and attachment state. File, spreadsheet, terminal and iWork batch reads use the original references, the smaller request/attachment limits, and original model destination and source labels; display names are not file-type authority. Expired, withdrawn or superseded selections are rejected, and oversized or image-bearing object results are not relabeled for model use. These checks do not replace capability grants or device-side reference validation, and do not establish complete mobile or permission-resume acceptance.

When a trusted runtime supplies explicit input-source labels, the shared Assistant loop preserves those sources instead of adding unrelated active attachments from the conversation. Model-output and owner-message provenance links remain attached; this bookkeeping does not authorize another read or export.

Permission continuations recover the conversation identity and original question from the authoritative session, including when a mobile client supplies only its session ID. The decision must still belong to that input. Before replaying the question to a model, the runtime validates its original source label and preserves sensitivity, destination and the stricter retention deadline; it cannot relabel expired, Secret or differently bound content as a new control message. For owner-attached objects, read grants on both Signal and Manager are limited to the original selection and read deadline, not attachments added while confirmation was pending or ambient device references. Approved conversation directories and verified file-result references are separate explicit selection routes: they require current directory consent, exact input, valid source evidence and a separately approved operation. An old input with no selector evidence cannot receive a new object-read grant, but its request can still be denied. Readiness changes do not refresh an existing grant.

Signal permission-decision retries return the original decision after current caller and connected-target checks, even if readiness is now unavailable, grants expired or were revoked, or a newer question superseded the input. The complete decision must match the original items and limits; item order may differ. A retry does not mint grants, restore uses, change the session, or start another model continuation. Missing or inconsistent request/decision records cannot be reconstructed from the current approval status. The returned `state` is a historical decision receipt, not current authority or proof that a continuation ran.

New decisions also persist a continuation fence in the same SQLite transaction. Signal periodically discovers unclaimed continuations without requiring the phone or original HTTP request to remain connected. It waits for an unambiguous authenticated target and fresh readiness, then revalidates the original input, model destination and current grants. Session claim and the transition to `started` commit together; duplicate wakeups cannot start the same continuation again. A newer question supersedes an unclaimed continuation. An already-started continuation is never automatically repeated after a crash: its original lease and action ledger are reconciled instead. These recovery checks do not renew references, grants or source retention and do not establish acceptance for all Providers or mobile runtime flows.

When AI Assistant accepts an in-flight follow-up, the shared loop rechecks the input revision at both the initial and final save boundaries so an old answer cannot become the result for a new requirement. Ordinary storage failures remain errors rather than being reported as supersession. Retracting an old answer does not confirm cancellation of a device action that already started.

The shared execution interface distinguishes runtime-confirmed non-execution from operator rejection. If an execution backend confirms an action was closed before dispatch, the loop records why it was not executed and stops further mutations in that turn, without calling it user cancellation. This internal outcome grants no execution authority and does not imply identical durable recovery support in every backend.

An execution backend may also supply a verified original result label. The shared loop checks that it matches the result bytes and preserves it without regenerating lineage or extending expiry at delivery time. A mismatch rejects the result without acknowledging delivery. The label grants no implicit model export permission. Open-source Signal persists original completion receipts for its bound, side-effecting Computer Action paths, including late results received after the foreground waiter exits. Foreground execution, active waiting and completion publishing use the same validated result projection. Legacy command results and inline browser reads retain their existing label paths.

With an explicit executor acceptance and a frozen background policy, a Computer Action can leave the foreground budget while remaining the same original task. Its owner snapshot reads conversation, grants and task state together; task changes advance the presentation sequence without invalidating a running turn's lease. Completion is saved before delivery is acknowledged, and expiry becomes unknown until a real result arrives. A bounded, tool-free model explanation requires the original, still-valid model/context export selection; Secret data, changed input/context/model, expired labels or unavailable replay cannot be silently reauthorized. The owner still retains the original result when automatic interpretation is denied. These original OSS tasks now support durable owner cancellation: only the original connection receives stop retries, never a repeated action or replacement connection. A stop acknowledgement remains nonterminal; only an original native pause receipt projects as cancelled, and a genuine late success or failure remains authoritative. This does not establish a complete lifecycle for every Provider or complete mobile-control acceptance.

A terminal receipt does not mean success. When a backend confirms failure, the shared loop preserves the original result label and acknowledges delivery only after saving, while reporting tool failure and stopping subsequent calls in the group. An actively awaited failure likewise retains the original action's call identity, not the wait call's. If that tool group is still open, the receipt remains unconsumed until a subsequent standalone wait retrieves it. Unknown effects remain unknown rather than becoming success or failure merely because a message arrived.

A transactional execution backend may return a version receipt bound to the original input, lease, call, and post-save session version. The shared loop accepts only its executor's consecutive version advances, including when a later step fails, so the error can be saved against the correct version. It never refreshes to bypass concurrent revocation or new input, and the receipt is not tool authorization. Open-source Signal defaults to its existing execution entry and requires no Manager shared storage for this interface.

Personal AI Assistant shares a compiled policy revision with Manager, independent of unrelated organization policy counters. Older decisions cannot be upgraded automatically and resumed. A new explicit request starts a turn under the current policy without relabeling history, reissuing old grants, or restoring their uses. Automatic continuation and grant issuance require the current revision; a match does not replace target readiness or grant revocation checks. Ordinary terminal Copilot policy semantics remain unchanged.

Browser Providers use shared closed-input preflight: input size is bounded, the selected BrowserSurface must be unexpired, and the server derives action scope and risk. Generic form filling and element activation remain InputFallback; Gmail/Slack draft handoffs do not become send actions. Passing preflight is not execution authority: the existing grant, egress, durable dispatch, and target-device checks still apply.

Semantic desktop execution, permission requests, and grant issuance share strict input decoding: only UiElement targets with Invoke, Select, Focus, Toggle, or bounded SetValue are accepted; Scroll remains unavailable. An application grant allowing Toggle does not imply every native control supports it. The original target still checks reference expiry, session identity, and actual supported actions. Central validation replaces neither native Accessibility/UIA execution nor local permissions, writer leases, or input takeover.

A centrally dispatched Computer Action does not require a browser to keep a remote-desktop connection open. Portable/DeskServer paths with an existing single worker can hand the action to that worker; session-targeted routing still requires an explicit binding and never guesses a desktop. Rejection inside the action handler before worker handoff reports definitely-not-started through `ComputerActionCompleted` correlated to the original request, rather than waiting for a timeout. This neither cancels other actions nor relaxes authorization, readiness, or local capability checks.

A trusted central service can request an original Computer Action stop with `CancelComputerAction`. The daemon validates authorization and forwards the approver plus the complete action/work/generation identity to the original worker; ambiguous sessions are never guessed. `CancelRequested` in `ComputerActionStateReported` only acknowledges invalidating the matching writer, not undoing an OS call or proving non-execution. Subsequent adapter steps are blocked, while the original completion or unknown result remains authoritative. Cancellation, preemption, and expiry retain the writer slot until the original operation releases it. Daemon and worker must use the same build: the cancellation IPC approver field cannot be mixed with the previous layout.

### Linux capability boundary

On Linux, the Assistant advertises each capability independently. System information, process and network inspection, container inspection, terminal-output reads, and owner-confirmed `bash`/`sh` execution use the same thin-edge and confirmation boundaries as Windows and macOS. On a booted systemd host, it also provides `systemd` service status and bounded `journald` JSON queries; those two capabilities remain visibly unavailable when `systemctl`/`journalctl` or the systemd runtime is absent, and journal visibility is limited by the Desk Server process permissions.

Explicitly selected Linux files and directories can be inspected without sending native paths to the model. Directory traversal and reads are handle-relative, reject symbolic links, revalidate object identity around bounded reads, and never recurse implicitly. Confirmed artifact creation is restricted to an exact device allowlisted directory and publishes a private `0600` staging file with Linux no-replace rename semantics, so an existing target is never overwritten.

Linux desktop UI inspection/actions, screen Computer Use, and browser Computer Use are not advertised yet. Chrome installation/profile detection exists for the future browser adapter, but it does not bypass the missing Linux interactive-session, foreground-window, protected-field, and local-input ownership safety proofs. Wayland remote-desktop capture is a separate transport feature and does not itself satisfy those Computer Use gates.

A headless `desk-server` is a pure thin edge: it has **no embedded signaling server**, so it must be attached to a remote central server (signaling server or manager) to use AI features. The portable `default` mode embeds the signaling server in the same process, so it remains self-contained.
:::

AI Assistant live Office, Numbers, Pages and Keynote reads now retain the selected device-issued document reference with the original input. Permission continuation does not select a newer foreground document. Reads recheck the original input, model destination, current worker/reference and original expiry before dispatch and after the result arrives; a changed or expired target is rejected without exporting its content. Office permissions use the same exact-object resource contract as live iWork permissions. Result provenance identifies the frozen target without exposing its executable token, and output retention cannot extend its deadline. Batch iWork still uses selected file attachments. A live input also requires the matching active durable 638 selection at intake and before read. Withdrawing that selection while permission is pending prevents resume without consuming the grant; selecting it again later cannot revive the old input. Android and iOS strictly correlate 639 and retry the same client request identity after reconnect. These checks still do not constitute full mobile-runtime or real-application acceptance.

Open-source Signal also revalidates the original input, current grant and readiness around each non-browser read. Grant limits narrow the typed request sent to the host and bound the complete returned payload, including error text and image metadata; oversized content is replaced by a fixed error and is never labeled for model use. A result label is bound to the exact validated bytes and expires no later than the original grant or selected data. If input or authority changes while a read is in flight, the received Provider outcome remains durably recorded but its content is withheld; a known response is not converted into an automatic-retry `OutcomeUnknown` state.

## Configuration

The **model provider** (provider, base URL, model, API key, output format, granted execution mode, per-turn reasoning-round limit, per-turn same-tool call limit, and command approval timeout) is configured on the **central signaling server**. The reasoning-round limit defaults to **40**, accepts **1–80**, counts model responses rather than individual tool calls, and cannot be lower than the same-tool limit. The same-tool limit defaults to **20**, accepts **1–50**, and counts calls to one tool type even when its arguments differ. Both are independent of the Desk Server's simultaneous-command-process limit. **API keys are strictly server-side secrets** — they are never returned to the browser, never written to logs, and never included in any public settings DTO.

The **command approval timeout** controls how long a newly suggested AI command waits for owner confirmation. It defaults to **120 seconds** and accepts **30–1800 seconds**. The signaling server freezes the value when it creates the approval, so changing the setting affects only later suggestions. The confirmation card shows this approval window separately from the device-enforced **command runtime limit**, which starts only after approval. This setting does not change the host ConfirmExec pending lifetime or the device's separate remote-access approval (Gate B) timeout.

A **Test connection** button next to Save probes the provider fields currently shown in the form, including unsaved edits, without persisting them. A text-only provider receives a tiny one-word chat probe; when **Supports image input** is enabled, the same button sends the repository-owned visual probe and succeeds only when the model reads its marker. The result reports the validated `text` / `image_input` capabilities. A blank API-key field reuses the stored secret; a newly entered key is used only for the probe until Save is selected. The API key stays server-side throughout.

The wire protocol is explicit and fail-closed: select `open_ai_chat_completions` or `anthropic_messages`; an empty, unknown, or reserved value is shown as unsupported and cannot be saved or tested. Standard, DeepSeek, Anthropic adaptive/manual, and Custom presets only populate explicit request options. The runtime never guesses behavior from a model or vendor name.

The OSS presets materialize Standard as `{}` with 512/4096 probe/runtime tokens, DeepSeek with thinking explicitly disabled and 512/4096, and Anthropic adaptive with `display: omitted` and 4096/8192. The manual preset is disabled because this singleton also serves terminal completion with a 512-token hard cap; use Custom only when the provider accepts a manual budget below 512. No preset fills `max_context_bytes`.

The form also requires a **history context byte budget** (`max_context_bytes`) between 4 KiB and 16 MiB. It measures the serialized conversation sent from local history, including tool-call/result and required replay state, but excludes separately injected system prompts, tool definitions, server-only metadata, and image data-URL bytes. It is not the provider's token context window. Neither the application nor the small connection probe can discover the true limit of an arbitrary compatible endpoint, so enter a conservative value from the upstream model documentation and actual request composition. Probe observations are revision-bound and become visibly stale after configuration changes.

Reasoning/thinking is private protocol state rather than answer text. It is not shown in the UI. When exact tool continuation requires it, the signal server may persist an opaque replay envelope (such as DeepSeek `reasoning_content` or ordered Anthropic thinking/redacted-thinking signatures and tool blocks). It is excluded from transcript responses, content-safety input, and logs, but can add to provider token usage.

Long conversations remain fully persisted and visible. After the configured high watermark is crossed, only a group-safe trailing window is sent to the model and that turn shows an inline notice explaining that older history was not sent. Nothing was deleted from the visible record. If the newest indivisible message/tool group alone exceeds the budget, the request fails with `AI_CONTEXT_ITEM_TOO_LARGE`; raise the configured budget or shorten the new input and retry.

Each device additionally keeps two **local** controls in its own settings: an **execution ceiling** (the highest mode the AI may use on that device, which caps any central grant) and an **evidence collection policy** (`allow_logs` / `allow_screen`, the device's final say over what evidence may leave it).

On Linux, the same local AI policy page also controls **one-shot PTY execution** for approved commands that need standard input. It is a machine-wide setting and is enabled by default; turning it off blocks new PTY dispatches but does not terminate a command that is already running. **Interactive elevation** is a separate, default-off subordinate setting. It remains disabled in the UI until the ServiceDaemon root-containment path is available. PTY input is relayed as ordinary bytes: the remote program controls terminal echo, and LCXL does not identify, retain, or add a separate password field for that input.

## Security

Device-read failures marked unsafe for the model become a generic tool failure before further model calls or conversation persistence. Internal error details are not included in that message.

The full set of invariants — server-side authority, fail-closed redaction, server-only keys, and metadata-only audit — is documented in the [AI Security Model](/security/ai-security-model).

In an automated task’s run details, you can review the requested directory, purpose, consent state and expiry in your current time zone, then approve, reject or remove an approved directory. Directory consent identifies a file scope; it does not grant read, write or send permissions. Actual operations remain subject to the task contract. The conversation refreshes after a decision; a recorded decision does not mean execution succeeded. Removing a directory that the task is waiting for ends that wait. Expiry of the original directory reference also ends the wait; the task does not automatically obtain a new reference or reuse the old consent. Neither action undoes operations that already occurred.

Use “Resume future runs” on a paused task to recheck its original authorization, contract, current device and model conditions. Resuming neither extends authorization nor catches up paused occurrences. “Run once now” creates a fresh occurrence for an active independent task without changing its calendar. “Cancel this run” in history targets only that occurrence; a cancellation request does not mean a dispatched operation has been undone.

Paused conversation continuations can also be resumed. The original requirement revision must remain unchanged, execution outcomes must be resolved, and the one-shot time must still be in the future; reschedule an elapsed time first. Resuming adds no conversation permissions, and execution rechecks current authorization.


You can also choose a device and an existing conversation from task management to create a one-time continuation. The list contains conversations available to the current owner; saving and enabling recheck the original requirement revision. Independent automations can start from a manually created draft or an AI proposal. Both require a guided run and explicit authorization.

The task list shows consecutive failures and the pause threshold. You can change the threshold while no run is active (default: 3). Raising it does not resume a paused task. Ordinary failures below the threshold allow the next scheduled occurrence; unknown outcomes or invalid authorization require resolution and explicit resumption.

Editing task instructions invalidates the previous authorization; independent tasks require another guided run and publication review. Editing timing alone does not expand permissions. Contract review shows authorization revisions and approval, expiry and revocation times, plus changes in budgets, permissions, steps, exception handling and instructions. Expand the previous contract to inspect its contents. Revoke task authorization pauses future scheduling and retains history; dispatched actions may still complete.

The OSS owner can configure server-wide independent task limits in **Settings → Scheduled task budgets**. Initial ceilings are 24 occurrences per UTC day, 64 tool calls, 100,000 model tokens and 900 seconds per run. Changes use a persisted revision check. Lower ceilings can block existing contracts; higher ceilings do not expand task permissions or resume paused tasks. Reload after a save conflict or uncertain response.

When rescheduling, the editor displays the existing rule in the selected time zone. Saving unchanged values preserves the UTC rule; changing the display zone projects the original rule again. After changing the timing, preview up to five future occurrences and confirm before saving. The server checks the conversion input and version again; changed results require renewed confirmation. Interval anchors are also converted by the server, then run at fixed elapsed intervals. Future times shown for paused tasks are a rule preview, not an indication that the task is enabled.

## While a background command is running

A conversation can track multiple background tasks, each with its own task ID for waiting, cancellation, and completion receipts. The controlled host atomically admits new commands up to its configured concurrency limit. At capacity it explicitly rejects the command without queuing or automatic retry. Synchronous queries remain available. Per-command authorization, exclusive desktop/browser writer leases, and inspection guidance for inconclusive outcomes still apply.

Background results are delivered automatically; polling and keeping the current AI turn open are unnecessary. In an interactive conversation, when no independent work remains, the assistant should briefly report that the task is pending and end the turn. Ending the response neither cancels the background task nor means that it has completed.

The composer toolbar always includes **Background tasks**, with a count of running tasks (including cancellation in progress). Open the side panel to view commands and background tools in the current conversation. Unfinished tasks appear first, followed by up to 50 recent command records. Expand a command to read its saved result; long results are truncated for display only. **Cancel task** targets that task alone, and its final status comes from the device or Provider receipt. Command cancellation requires a connected device; saved records remain viewable offline.

When a model returns readable reasoning, committed assistant messages include a **Thinking** section that is collapsed by default. Expand it to read the reasoning separately from the answer; it remains available after reload and in conversation history. Long reasoning is bounded for display. No section is shown when readable reasoning is absent, and signatures, encrypted content, and internal protocol replay fields are never displayed.

Completed tool results and assistant replies remain part of the conversation when a later message has no new context selection or a tool grant is exhausted. New reads and actions still require authorization. History is summarized or trimmed when the context budget requires it; restoring an interrupted conversation preserves unknown action outcomes as unknown.

On macOS, **List applications** returns regular desktop app names and lifecycle-bound selection references. Select an app to read its windows and controls even while it is in the background. Listing does not inspect every app’s UI or activate an app. AI can use the same selection flow after read approval; actions require separate confirmation. Foreground changes preserve the selected application identity, but process restarts require a fresh selection; local policy changes still fence access. Apps may expose incomplete Accessibility data; an empty observation does not prove an app is closed.

For ordinary desktop UI actions (invoke, select, focus, toggle, and set value), success confirms completion of the native Accessibility/UIA API call only. The host does not compare UI trees or read back attributes to judge the intended effect. The AI must inspect the UI separately after an action, decide its next step from that observation, and obtain the required authorization. Unknown execution outcomes such as timeouts or disconnections must never be blindly retried.

UI tools return model receipts containing object IDs and kinds; snapshot metadata and reference expiry remain on the server. Null fields and empty action lists are omitted. Controller observation panels and device wire payloads keep their full structure. For truncated results, the assistant should increase the bounded depth/node budget or inspect an exact window. Exhausted or naturally expired approved read permissions can be requested again, with a new owner decision; denied or revoked authority is not restored automatically.

UI inspection supports three `scope` values: `content` (default) reads ordinary UI, `menus` reads only menus for a follow-up search, and `all` reads both. For the macOS application menu bar, use an application root or the default foreground application; a window root only reads menus within that window. Scope selection does not replace read authorization or action confirmation.

Application, UI, process and service searches use top-level `queries` (up to 16 terms, each at most 128 UTF-8 bytes): case-insensitive substring matching with OR semantics, no regex or spelling correction. Services match names and display names before truncation; unmatched searches return an empty list. The old UI `query` object, exact name/native-ID/role selectors and service `name` are removed. Known controls can use top-level `element_id` or `root_id` with `element_only=true`. Unfiltered listings require explicit `allow_unfiltered=true`.

Both screenshot modes remain available: `read_current_screen` without `window_id` captures the full currently selected display. Passing a window ID from `owner_selectable_windows` as `window_id` uses independent window capture on macOS, including when another window covers it, without activating it. Minimized windows without a fresh frame fail explicitly; restoring them still requires action authorization. Window selection never bypasses capture permission. When an image becomes text-only history, the system validates the original receipt and derives a new content binding with the same sensitivity, model authorization boundaries, and source lineage, so the next turn does not fail on stale size or digest metadata.

Model history auditing processes complete records within the content byte budget, without failing solely at 64 messages or 256 response sources. Every record still has its digest and model destination checked; source metadata has a separate byte limit. Capacity, integrity, and permission failures are reported separately. Loading tools preserves the current loaded set by default; the assistant can explicitly replace it when count or description budgets require it. Loading does not grant permission.

Desktop UI action permission batches include desktop session and UI reads on the current device by default, excluding screenshots, so the assistant can check the result afterward. Included reads use the action request duration and allow up to 16 calls each. They are separately displayed and selected by default; the owner may shorten, narrow, or deny them. Existing narrower read requests are preserved. Native UI actions require an approved application scope and action set, bounded by expiry and remaining uses; exact target/action approval is no longer supported. Reads and actions can be revoked separately; every call still checks conversation authority, application ownership, and local capability.

New conversations preload at most four read tools into an eight-tool working set, leaving room for on-demand discovery. Callable reads come first; within each group, desktop session, application/UI discovery, processes and system information take priority. Writes are loaded explicitly. Built-in conversation tools such as permission requests and task status need no loading and do not consume these slots; mistakenly requesting them returns explicit recovery guidance. Count or description-size errors include the currently loaded tools, count limit, and explicit replacement instructions. Failed loads leave the working set unchanged and never automatically unload tools.

## Conversation screenshots and context

AI Assistant screenshots are stored as separate conversation attachments. Reloading, reconnecting, and context compression do not delete them. The conversation lets you view full images, load more images, or delete an individual image. The stored image is the reviewed screenshot supplied to the model for that tool call; a new capture never substitutes for a historical image. Pixels discarded by earlier versions cannot be recovered.

Images enter model context only when needed. Text history retains the original tool-call reference; compression does not clean up attachments. The assistant can use `read_conversation_image` to list references and retrieve an image by `attachment_id` or an unambiguous original `tool_call_id`. Retrieval checks the current model destination and applies image safety review again. Switching models does not automatically authorize exporting old images, and historical images neither restore expired UI references nor count as fresh screen observations.

OSS / Tauri stores image files in `assistant-images/` under the local data directory, with metadata in SQLite. Manager stores metadata and binary images in shared PostgreSQL tables, accessible across instances. Conversation JSON contains no image pixels. Images retain the model input limit of 400,000 bytes each; a conversation has a 100 MiB attachment quota. Exceeding the quota fails explicitly instead of deleting older images.

Attachments follow the conversation lifetime. Deleting an image or its conversation immediately prevents subsequent image reads; background cleanup removes files or binary data. Individual deletion tombstones remain until the conversation is deleted so replay cannot restore deleted images. Compression and permission expiry do not delete attachments. Existing conversation retention settings still apply.

To reduce context use, the assistant should prefer known element references or fuzzy `queries` across native identifiers, roles and names after its initial UI read. Permission proposals identify a tool name; the server derives its Provider and effect. Inactive grants are grouped by tool and state, while active exact action arguments remain available for verification. Permission expiry does not prematurely trim historical tool results.


When AI requests a conversation timer, only a pending review request is saved, not a task draft. The current turn waits for the owner decision while an inline approval card in the conversation shows the task and execution time with explicit Approve and enable / Reject actions, matching permission-request styling. No further model call runs during this wait. The server returns approval or rejection to the same turn before AI continues. Stop ends the wait without automatically approving the request. Approval creates the scheduled task. The card has no dismiss action: only an explicit approval or rejection submits a decision. Multiple requests can remain visible together. The card displays the result after server acknowledgement; a failed request remains visible for review and retry. Pending and rejected requests are excluded from task lists. No chat confirmation is needed. An enabled conversation timer survives ordinary follow-up chat, including “confirmed”; only an explicit pause or cancellation stops scheduling. When due, it waits for the conversation to become idle and executes the approved task text in the latest conversation context. Dispatch pins the current input revision, so new input during execution still fences the older turn. Permissions are rechecked without extending expiry or scope.

Relative requests such as “in five minutes” count from successful server activation after confirmation. The pending review retains and displays the delay without calculating an absolute execution time; activation stores an absolute UTC instant, displayed in the selected timezone. The activation receipt is preserved in the original conversation without creating new user input or granting tool permissions. Independent automations still require rehearsal, permission review and publication.

The assistant can query current-conversation tasks with `list_conversation_scheduled_tasks`, including server state, creation source, execution time and cancellation eligibility. It can cancel AI-created tasks with `cancel_conversation_scheduled_task` without another permission request or approval dialog. Manually created tasks are read-only to AI and must be cancelled by the user in task management; requesting permission cannot bypass this boundary. Origin is recorded by the server at creation; approving an AI proposal does not make it manual. Cancellation stops future scheduling and requests cancellation of any started occurrence, without undoing external effects.

After a service restart or interrupted execution, an expired execution lease no longer keeps the conversation marked as running. Refreshing the server snapshot clears a pending stop and allows a new conversation while retaining history. Background commands retain their independent lifecycle and are not cancelled by this recovery.

You can create or switch conversations while another runs in the background. The conversation list shows a spinner for active conversations and sorts running conversations first, then by most recent activity within each group. Deletion requires confirmation, with an additional warning for a running conversation. It removes history and images, stops further AI processing and cancels associated conversation timers. Background commands receive best-effort cancellation; stopping is not guaranteed and completed actions are not undone.

The composer stays at the bottom of the assistant page or remote desktop assistant panel. Messages scroll independently and follow new content by default. Scrolling up pauses following; use “Jump to latest message” or scroll to the bottom to resume. Switching conversations opens the latest messages.

“Scheduled tasks” to the right of session directories opens timers for the current conversation, including completed tasks. Only pending approval cards remain in the conversation area. Tap the context usage ring for details; composer buttons and the conversation list, resume timer, and new conversation header buttons hide their labels when space is limited.

On macOS, semantic UI actions relocate and validate the original process and element after approval. Human input preempts execution but approval clicks do not erase semantic target identities. Coordinate snapshots and worker restarts retain their invalidation rules. When a native action fails or its effects are uncertain, the assistant receives its error and inspects the current application state. Other authorized writes remain available and no owner acknowledgement or record closure is required. Keep the original receipt and avoid blind duplicate execution.

Unresolved operation cards show the operation category, receipt uncertainty, and checking steps. Request and execution identifiers remain in collapsed troubleshooting details. The card states when no specific error reason is available.

Failed or unresolved actions show the original request reason associated with the grant actually reserved for that execution. The link uses server work and grant-use records, never timing or approximate input matching. A reason explains the intended operation, not its error cause, and grants no new authority.

### Stable UI element identities

Each UI element's `element_id` equals its `object_ref.token` and identifies one native element within the controlled worker. Repeated reads, different searches, text/value updates, and grant expiry or renewal do not allocate a new ID. macOS compares retained AXUIElement objects; Windows uses process-lifetime RuntimeIds and retained UIA elements. Tree positions, labels, and coordinates are not element identity. Destroyed/recreated elements and restarted applications receive new identities; worker or desktop-session replacement invalidates the old IDs.

Desktop references follow native object lifetimes, with no fixed expiry. Re-reading an unchanged application or control preserves its ID and reuses its stored mapping. Objects destroyed or recreated, applications restarted, and worker/session replacement invalidate references; current native ownership and authorization are still checked before execution. Permission duration and uses follow the owner’s approval and are never shortened by a reference deadline. The bounded store reclaims invalid UI mappings when needed and rejects new allocations if capacity remains exhausted, preserving existing live IDs.

### Conversation grants and native value types

Grants apply to the current conversation and approved scope. Ordinary follow-up messages such as “continue” neither invalidate grants nor clear loaded tool details. Expiry, usage limits, revocation and exact action inputs still apply. When permission is missing, the assistant submits the approval card directly, batching operations whose inputs are already known instead of asking for another confirmation in chat.

On macOS, `set_value` preserves the native value type: text uses strings, numbers require finite decimals, and dates accept RFC3339 with an explicit offset, `YYYY-MM-DD` (preserving local time), or `HH:MM[:SS]` (preserving the local date). Reads expose dates with their time zone offset. Invalid formats and unsupported types return actionable errors before any write.

### Application-scoped permission and control search

For multiple native UI steps, the assistant can request application-scoped permission in the current conversation. The review card shows the application name obtained from device observations and the permitted click, select, focus, toggle or fill actions. Owners can narrow actions, duration and uses. Every operation still checks conversation authority, the control’s actual application and process identity. Other applications, raw mouse/keyboard input and screenshots are outside this action permission; desktop reads appear as separate review items. Application restart requires fresh observation and approval; reference age does not shorten permission. Native UI actions exclusively use application-scoped approval.

Ordinary messages, permission continuations and conversation schedule resumes restore tools from effective database grants. A new message does not discard existing permission. An invalid permission batch creates no review card, including for otherwise valid items; the assistant receives the invalid item, required input structure and prerequisite-read guidance.


Native UI permission requests use `application_scope` exclusively; `exact_input` is rejected. Every execution requires the approved `application_id`, an observed `element_id` and `action`. Loading tool details does not create an approval request. The assistant may report a submitted card only after `request_capability_grants` returns a successful `request_id` with `pending_user_decision`.


Desktop UI tools expose IDs to the model: reads take optional `root_id`, semantic actions take `application_id`, `element_id` and `action`, application permission requests take `application_scope.application_id`, and window screenshots take `window_id` (omitting it still captures the current display). The model supplies neither snapshot IDs nor reference expiry. The server resolves full references from observations in the current conversation and continues to validate native lifetime, object kind, application ownership and authorization. A partial read never replaces references for other controls. Invalidated references explicitly require another read; unknown IDs neither trigger unfiltered searches nor request new permission automatically. Historical observations remain intact, and native object lifetime and permission validity are checked separately. Windows fallback input also uses `application_id` while retaining exact-input approval.

Tool calls appear in conversation order as collapsed records. Expand a record to inspect the tool name, input, and returned output (including errors). Live records update when results arrive, and saved records remain available when reopening the conversation or loading earlier messages. Missing results are shown explicitly; only data retained by the server can be displayed.

Device capability readiness reports remain valid for 60 seconds and refresh every 25 seconds. Diagnostic logs identify delayed/slow collection, reporting channel closure, invalid or expired reports, and missing fresh readiness at execution, without recording UI contents or tool payloads.

UI search guidance combines localized labels with English names, native identifiers and control types (at most 16 alternatives per batch), including date/time/input on a Chinese UI. A search miss does not establish that a feature is unsupported. When an entry button supports activation and the application grant permits it, the assistant should open it and inspect the resulting controls itself. It must verify the actual edited control and outcome, rather than treating a quick-entry field or existing event as proof of completion. Desktop references follow native object lifetimes; grant duration and uses are checked separately. Each model request includes current UTC time; device-local dates and timezones still require current device/application evidence or explicit user instructions, never inference from language or the server timezone.

### macOS background mouse and keyboard (experimental)

Prefer semantic UI actions. When semantic UI cannot express the operation or observations and results show it is impractical or unreliable, combine background input with a current screenshot of the target application window. Obtain that screenshot with `read_current_screen` and `window_id`, refreshing it when needed. Do not default to background input when a suitable semantic UI action can accomplish the task.

`execute_background_inputs` supports click, double click, scroll, Unicode text input or named key with modifiers to an observed application window. It accepts application/window IDs. Click/double-click accept either a control ID or original window screenshot pixel coordinates; scroll requires screenshot pixel coordinates (top-left origin; x < image width, y < image height). The server resolves PID, geometry and reference metadata. Mouse clicks currently use the primary button; dragging is not supported.

The permission card approves an application and action scope in the current conversation, with editable duration, use count and actions. Approved operations reuse that grant and include desktop/UI observation; screenshots require separate permission. Background input and semantic UI actions use separate tool grants. Existing device application access rules still apply.

Delivery does not activate the application, move the real cursor or fall back to foreground input. Keyboard input requires the requested window to be the application's keyboard input window. Minimized or ambiguous windows are rejected. Coordinate input needs a window screenshot and must refresh it after a resize; control-based input uses current control bounds. Human input in other foreground applications does not preempt background delivery. Stopping the conversation cancels subsequent events, but cannot retract events already sent.

A receipt confirms event dispatch, not application state. The AI should read the UI or screenshot afterward. Failures explain the cause and, after partial dispatch, the number of events sent; they do not require an owner outcome acknowledgement or block subsequent authorized actions. Mouse delivery probes a private macOS API at runtime; unavailable mouse support does not disable keyboard input. TextEdit was tested on macOS 15.6.1. Background Command+A did not work in that environment; other applications and OS versions may behave differently.

### Batch UI and background input (trial)

The AI currently sees only `execute_ui_actions` (semantic UI) and `execute_background_inputs` (background mouse/keyboard). Single-action entry points are hidden. Use `steps` with 1–20 entries, even for one action. Each batch targets one application; background batches also bind one window. The two action families are not mixed in a batch.

Existing application approval must cover every action kind. One batch consumes one grant use. A sealed batch holds one writer lease, executes sequentially and stops at the first error, without rollback or automatic retries. Existing 30-second dispatch deadlines and authorization/cancellation constraints still apply.

There is no fixed inter-step delay beyond native input event timing. Split asynchronous dependencies such as opening windows or changing layouts into separate batches with a UI/window screenshot read between them. Prefer semantic UI; use background input with a window screenshot only when semantic actions are impractical.

Success returns the completed count. An execution failure returns only the failing step number, its error and whether that step may have taken effect. Earlier steps completed native dispatch; later steps did not run. Whole-batch preflight failure explicitly reports that no steps ran. Original arguments remain in the folded tool record. Native dispatch does not verify the intended application state: the AI must read back. Errors need no user acknowledgement and do not block new authorized calls.

For macOS application tasks, first search running applications by localized and English names, then inspect controls using the returned application ID. If a complete application search finds no match, launch the app through an authorized mechanism and query again; do not repeatedly increase control search depth or equate a non-running app with an uninstalled app. An observed foreground reference already identifying the target app can be used directly. Application discovery still requires search conditions; request an unfiltered list explicitly only when necessary.

Application entries expose `application_state`: `foreground`, `background`, or `hidden` (which takes precedence). The field is omitted when unavailable. Application entries omit `matched_queries`; control searches retain match indices. This state does not indicate window minimization, occlusion, or visibility across desktop spaces.

Collapsed tool records show status icons: a green check for success, a cross for failure, and a spinner while running. A stopped conversation with no tool result shows a neutral unknown icon rather than an assumed outcome. Icons include accessible labels and hover descriptions.

Screenshot safety checks on macOS scan reachable Accessibility children independently of model UI response limits. The scan reads control subroles and child relationships without collecting text or adding a UI tree to model context. Protected controls block capture; an unreadable tree or a 10-second scan timeout reports an incomplete safety check instead of claiming a protected control was found.

For a macOS application screenshot, the assistant first searches the running application catalog, then queries the returned application ID with `queries=["窗口", "window"]` to discover windows, and passes the returned window ID to the screenshot tool. Application catalogs do not query windows: model results omit empty window lists and explicitly explain the next lookup.

Failed macOS screenshot safety scans log a scan ID, PID, scan scope, node position, role/subrole, AX status and timing. Failure-only probes report whether the attribute is advertised and the child-count API result. Logs exclude control titles, values and calendar text; diagnostic probes do not bypass protection or retry capture.

Window screenshots check the selected application and window rather than the unrelated foreground application. Full-display screenshots retain foreground checks. The host application menu bar’s `AXChildren` error `-25200` is logged and that branch is skipped; other controls remain scanned and other read failures still block capture.

Exact window screenshot approvals bind the observed window ID consistently before and after server reference resolution. Server-added reference metadata does not invalidate approval; another window, a different display selector, or full-display capture does not match that exact approval. Native object validity and current authorization remain checked at execution.

macOS screenshot scanning checks sensitive input controls rather than requiring optional subroles on ordinary groups or buttons. Hidden subtrees, minimized windows, and sensitive inputs with zero visible area or outside window/scroll clipping are ignored. Partially visible inputs remain checked, and missing visibility metadata does not imply invisibility. Background-window capture does not treat coverage by another application as hidden content.

After receiving a screenshot, the assistant may perform authorized targeting in the next model step without taking another screenshot. Screenshot and targeting in the same assistant batch remain blocked, and these rejections count toward the repeat limit. Window geometry remains available from stored screenshot receipts even after the image placeholder is appended.

UI search results include `location.status`. On macOS, controls with available geometry include visible `bounds` (`x`, `y`, `width`, `height`, in original window screenshot pixels, top-left origin) and their owning `window` reference. The coordinates use the same window space as background input. Hidden, outside-visible-area and unavailable locations are explicit; other adapters currently report unavailable. Match names, roles and location together. If a scroll area is ambiguous, use a current application screenshot to choose the intended region. After input, read back before claiming success; unchanged content calls for reconsidering the target, not repeatedly increasing scroll distance.

Screenshots appear inline immediately after their associated tool record and before the subsequent assistant reply. Earlier images whose messages are not loaded or have been compacted appear at the start of the transcript; loading earlier messages restores their inline placement. Image viewing, deletion and pagination remain available.

Background scrolling uses `horizontal_pixels` and `vertical_pixels`: these are pixel distances, not wheel ticks or lines. For example, `vertical_pixels: -300` scrolls down 300 pixels, while `-6` moves only six pixels. Message input remains in the composer until the server confirms acceptance. After 15 seconds without confirmation, use “Check and retry”; it checks stored messages first and resends the original message ID if still unconfirmed. Sending, acceptance and timeout diagnostics log identifiers only, never message text.

Background scroll requires an explicit `position: {x,y}` in the current original window screenshot; `element_id` is rejected for scroll (click/double-click still support it). Choose a point inside the intended content, avoiding sidebars, toolbars and dividers. A successful batch optionally includes `last_scroll` with the last dispatched pixel position and distances, without returning successful step history. This receipt does not verify content movement. Read UI or a screenshot afterward; unchanged content requires reconsidering the target before increasing distance, and repeated failure must be reported accurately.

Execution receipts omit the constant `application_state_verified` field. `status` describes native dispatch only; the assistant checks the intended outcome by reading UI or screenshots.
